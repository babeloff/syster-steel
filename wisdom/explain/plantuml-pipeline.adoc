= The SysML v2 → diagram generation pipeline
:description: Architecture of the model-to-diagram transformation pipeline
:icons: font

== Overview

The pipeline has two parallel output paths from a shared data-transformation
stage.  Both paths are exercised together when you run `pixi run gen-diagrams`
or `pixi run gen-self`.

----
SysML v2 text file
        │
        │  syster/parse-file          (steel-core Engine::run)
        ▼
   SysmlModel (HIR)
        │
        │  syster/file-symbols
        ▼
   list of HirSymbol
        │
        │  Steel script (filter + build data hash)
        ▼
   data hash (hash-maps and lists)
        │
        ├─── hbs/render  (Handlebars template in steel/templates/)
        │              │
        │              ▼
        │       PlantUML source (.puml)   ← kept for reference / manual use
        │
        └─── dot.scm  (DOT language generator)
                       │
                       │  layout/render-dot  (Rust binding, layout-rs crate)
                       ▼
                SVG  ← primary rendered output
----

image::../diagrams-gen/pipeline-flow.svg[Diagram generation pipeline action flow,width=600,align=center]

Each stage is independent and composable.
You can stop at any point —
for example, to inspect the symbol list before generating diagrams,
or to post-process the `.puml` source if you have plantuml installed locally.

== Stage 1: Parsing — `syster/parse-file`

The Rust function `syster/parse-file` is registered with the embedded `Engine`
and invokes syster-base's parser pipeline:

. The *lexer* (logos) tokenises the source text.
. The *parser* builds a rowan Concrete Syntax Tree (CST).
. The *AST layer* wraps CST nodes in typed structs (`Definition`, `Usage`, …).
. *HIR extraction* (Salsa queries) flattens the tree into `HirSymbol` values
  and resolves qualified names where possible.

The resulting `SysmlModel` is an opaque handle wrapping the Salsa database.
Multiple calls to `syster/parse-file` return independent model values;
they do not share state.

== Stage 2: Symbol extraction — `syster/file-symbols`

`syster/file-symbols` runs `extract_symbols_unified` from syster-base,
which returns all `HirSymbol` values in definition order.
The list is flat: nesting is encoded in qualified names, not in a tree structure.

Filtering is the first job of the Steel script.

[source,scheme]
----
; Only part definitions
(filter (lambda (s) (string=? (hir-symbol/kind s) "PartDefinition")) syms)

; Everything under one package
(filter (lambda (s)
          (starts-with? (hir-symbol/qualified-name s) "VehicleModel::"))
        syms)

; Elements exposed by a specific view
(define (exposed-by? sym view-sym)
  (let ([exposes (hir-symbol/view-expose view-sym)])
    (any (lambda (path)
           (starts-with? (hir-symbol/qualified-name sym) path))
         exposes)))
----

== Stage 3: Data transformation

Each diagram type is a function that maps a filtered symbol list to a Scheme data
hash (nested hash-maps and lists).
The data hash captures the diagram's content — definitions, relationships,
state transitions — in a form that is independent of any output format.

[source,scheme]
----
; build-bdd-data returns a hash ready for hbs/render
(define data
  (hash "title"        "Vehicle System"
        "theme"        "plain"
        "definitions"  (list (hash "name" "VehicleSystem" "attrs" ...))
        "compositions" (list (hash "parent" "VehicleSystem" "child" "Engine"
                                   "role" "engine"))))
----

== Stage 4a: Template rendering — `hbs/render` → `.puml`

`plantuml.scm` passes the data hash to a Handlebars template via `hbs/render`.
Templates live in `steel/templates/` and declare the PlantUML structure;
scripts supply only the data.

[source,scheme]
----
(hbs/render *hbs* "bdd" data)   ; renders steel/templates/bdd.hbs
----

The output is a `.puml` source file that is written to disk for reference.
If you have plantuml installed locally you can render it manually;
see xref:../instruct/render-diagrams.adoc[How to render diagrams] for details.

To customise output, edit the `.hbs` template or point `*templates-dir*` at your
own template directory before requiring `plantuml`.

The `hbs/*` functions are registered automatically at engine startup.
See xref:../refer/hbs-bindings.adoc[Handlebars Steel bindings reference] for
the full `hbs/*` API.

== Stage 4b: DOT generation and layout — `dot.scm` + `layout/render-dot` → SVG

`dot.scm` contains DOT language generators for all eight diagram types.
Each generator takes the same filtered symbol list and produces a DOT graph
string.  The DOT string is passed directly to `layout/render-dot`, a Rust
binding to the `layout-rs` crate, which applies the Sugiyama hierarchical layout
algorithm and emits an SVG string — the same algorithm family used by Graphviz's
`dot` command and PlantUML's built-in Smetana renderer.

[source,scheme]
----
(require "dot.scm")

; Generate DOT source for a BDD
(define dot-text (generate-bdd-dot symbols))

; Render DOT → SVG in-process (no external binary needed)
(define svg-text (layout/render-dot dot-text))

(write-string-to-file svg-text "vehicle-bdd.svg")
----

This path requires no Java installation and no external `plantuml` binary.
SVG output is produced entirely within the Rust process.

== Stage 5: PlantUML examples

=== Block Definition Diagram

Selects `PartDefinition` and `PortDefinition` symbols,
renders each as a PlantUML `class` with `<<block>>` stereotype,
and derives composition lines from `PartUsage` relationships.

[source,text]
----
@startuml
class "VehicleSystem" <<block>> {
  + mass : Real
  ~ drivePort
}
class "Engine" <<block>> { … }
"VehicleSystem" *-- "Engine" : engine
@enduml
----

=== Internal Block Diagram

Selects a single `PartDefinition`,
renders its `PartUsage` children as components,
and maps `ConnectionUsage` entries to connector lines.

[source,text]
----
@startuml
component "engine : Engine" as engine
component "chassis : Chassis" as chassis
engine -right-> chassis : driveShaft
@enduml
----

=== Package Diagram

Selects `Package` symbols and `Import` relationships,
rendering packages as namespaces and imports as dashed arrows.

== Stage 5: Output

Running `pixi run gen-diagrams` (or `pixi run gen-self`) produces two artefacts
per diagram:

* A `.puml` file written by `plantuml.scm` via `hbs/render`.  This is kept for
  reference and for manual rendering if plantuml is separately installed.
* An `.svg` file produced in-process by `dot.scm` + `layout/render-dot`.
  No Java or external binary is required.

If you do have plantuml installed, you can render a `.puml` file manually:

[source,shell]
----
plantuml -svg vehicle-bdd.puml
----

[cols="1,1,3"]
|===
| Flag | Format | Notes

| `-svg` | SVG | Scalable; preferred for documentation
| `-png` | PNG | Raster; good for inline images
| `-pdf` | PDF | Suitable for print documents
| `-txt` | ASCII art | Useful for terminals
|===

== Why Handlebars templates?

Separating the data-building step (Steel scripts) from the formatting step
(`.hbs` templates) keeps each concern in its natural representation.
Scripts work with typed SysML data; templates declare the PlantUML structure.
Changing diagram style — adding skinparam directives, switching layout direction,
reformatting class boxes — requires editing only the template, not the script.
Conversely, adding a new symbol kind to the diagram requires editing only the script.

== Why two output paths?

The `.puml` path (Handlebars templates) was the original approach.
PlantUML's text format is human-readable and diffable,
making it useful when checking diagram source into version control.
It is preserved as a reference output and for users who want to customise
diagrams with PlantUML's rich skinparam vocabulary.

The DOT path (`dot.scm` + `layout/render-dot`) was added to remove the Java
dependency.  Graph layout — routing edges, avoiding overlaps — is handled by
the `layout-rs` crate's Sugiyama algorithm, which is the same hierarchical
layout family used by Graphviz's `dot` command and PlantUML's Smetana renderer.
SVG is produced entirely in-process, with no external binary required.

== View-driven generation

SysML v2 has a first-class concept of *Views* and *Viewpoints*:

* A `ViewDefinition` declares _what_ should appear using `expose` clauses.
* A `ViewUsage` instantiates a view for a specific scope.

The pipeline can honour these by filtering the symbol list to only those elements
exposed by the relevant view before calling the PlantUML generator:

[source,scheme]
----
(define view-sym (syster/find-by-qname all-syms "VehicleModel::SystemView"))
(define exposed  (filter (lambda (s) (exposed-by? s view-sym)) all-syms))
(write-plantuml-file (generate-bdd exposed) "system-view-bdd.puml")
----

This aligns the generated diagram with the modelling intent,
rather than dumping every element in the file.
